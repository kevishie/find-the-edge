01 · PRODUCT DESIGN DIRECTION

A professional betting terminal crossed with a modern analytics product. Density and speed over decoration. Evidence over hype: every claim of value is traceable to fair-odds math, a book count, and a freshness timestamp. Confidence and expected value are shown as separate signals so a high-EV / low-confidence play is never mistaken for a sure thing.

BANNED COPY: lock · guaranteed · risk-free · can't lose

02 · INFORMATION ARCHITECTURE

Terminal / Dashboard — where is the edge now
├ Events → Event Detail → Scouting Report
├ +EV Scanner · Odds Terminal · Watchlist
├ Scouting Reports (library + versions)
├ Bet Tracker → Performance (CLV, calibration)
└ Data Sources · Settings

03 · PRIMARY USER FLOWS

Dashboard → placed bet (the core loop)
Dashboard top +EV card → Open Event → read Scouting Report (esp. Market Edge) → Final Plays → Add Bet (pre-filled ¼-Kelly stake) → confirm → lands in Bet Tracker as OPEN with source link.
Manual scouting
Events / Event Detail → Scout Event → job enters queue (QUEUED → IN PROGRESS with live section-by-section fill → COMPLETE). Failures surface a retry with partial-data fallback.
Automatic scouting
Scheduled per Settings (leagues + cadence). New results appear as a new report version with a "changes since previous" diff and a dashboard "recently completed" entry.
Bet ↔ recommendation linkage
Every bet stores its source (Scanner rec # or Report version). Bet Tracker rows deep-link back so Performance can attribute CLV to the model version that produced it.
Why the system believes there's value
Market Edge section states it plainly: no-vig fair prob vs Hard Rock implied prob, the gap, the corroborating book count, and supporting line movement — the whole argument on one screen.

04 · RESPONSIVE

  • 1440 desktop = primary; 1280 laptop = same layout, tighter gutters
  • 768 tablet: rail collapses under content; tables scroll-x
  • 390 mobile: single column — current +EV, event status, odds, report summary, bet-entry only. No full terminal.

05 · ACCESSIBILITY

  • Status never by color alone — always icon/label + color
  • Body text ≥ AA contrast on #0A0A0D; numerics in mono for scanability
  • Keyboard: nav, sort, tab-to-row; visible focus ring in purple
  • Live regions announce odds refresh + stale warnings

07 · DEVELOPER HANDOFF NOTES

  • All odds stored American; convert to decimal for math. No-vig fair prob = normalize implied probs across books, then average (book-weighted per Settings).
  • EV% = fairProb × decimalOdds − 1. A play qualifies at EV ≥ threshold AND books ≥ min AND age ≤ max (Settings-driven).
  • Freshness is a function of last_updated vs maxOddsAge: fresh ≤ 5m, aging ≤ 10m, stale > 10m — recomputed client-side each render.
  • Confidence is a model output independent of EV; render as its own meter, never fold into the EV color.
  • Reports are versioned append-only; diffing compares section hashes to flag "changes since previous".

08 · OPEN UX QUESTIONS

  • Should qualified +EV exclude thin (<5 book) markets from the dashboard, or show with a warning? (Currently: show + warn.)
  • Auto-refresh cadence vs API quota — poll interval or manual only?
  • Kelly: expose the fraction per-bet, or global in Settings?
  • Live in-play scanning in MVP or v2?
  • How aggressively to alert on stale Hard Rock feed?

09 · IMPLEMENTATION ORDER

  1. Auth + shell + Data Sources (prove the pipeline)
  2. Odds Terminal + fair-odds/EV engine
  3. +EV Scanner (the daily driver)
  4. Dashboard (aggregates the above)
  5. Event Detail → Scouting Report + versioning
  6. Bet Tracker → Performance (CLV loop)
  7. Events Explorer, Watchlist, Settings polish

Mobile is a distilled companion, not a shrunk terminal. It surfaces only what drives an on-the-go decision: current +EV, event status, odds, the report verdict, and one-tap bet entry. A bottom tab bar replaces the sidebar.

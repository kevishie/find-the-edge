# Completed-result ingestion

The result schedule is intentionally disabled while no production adapter or participant mapping exists. The deployed handler also fails closed with `completed-results-runtime-not-configured` on every manual invocation, so fixture wiring cannot report false production success. Fixture adapters are exercised only by automated acceptance tests. The schedule and handler must not be enabled until an authoritative production result adapter and exact participant mappings are configured and reviewed. Once enabled, the hourly worker polls a rolling 72-hour window for MLB and MLS. Operators may submit a manual `commands` array, limited to 12 strictly validated commands, with each command bounded to 31 days, 20 pages, and 100 records per page.

Finals can arrive late. Re-running the same window is safe: an exact replay does not add history, while a provider correction with higher revision authority appends a new version and advances the single cross-provider current projection. Older arrivals remain in immutable history but cannot replace current truth. Result, unresolved, and audit-history reads use bounded cursor pages. Provider cursors and their original polling window are durably checkpointed after every page so a `maxPages` boundary resumes on the next invocation rather than truncating the feed.

Results without an exact provider-event mapping, including participant scope mismatches, are stored under `UNRESOLVED_RESULT#<provider-id>`. Repair the schedule/provider mapping and replay the bounded window; never create or name-match an event from a result. Postponed, cancelled, and no-contest records must not carry scores. Missing overtime or extra-inning semantics remain `unknown`.

Alert on worker errors and sustained hourly lag. Every league run and its counters/failure code is persisted before the invocation returns. All independent commands finish; any failed run then fails the invocation so Lambda retry and alarms activate. Logs and failures contain stable reason codes only; credentials and licensed raw payloads must never be logged. The worker uses the existing event table and only `DeleteItem`, `GetItem`, `Query`, and conditional `PutItem`; it has no scan permission and no unrelated secret access.

Rollback by disabling the `CompletedResultsScheduler` rule. Keep the append-only records for audit and deploy the prior worker version; never delete or rewrite correction history.
